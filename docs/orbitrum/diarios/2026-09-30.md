## VISÃO + CONCLUSÃO (cruzando a tese e todos os docs — 30/09)
**O que o Orbitrum é (destilado):** uma infraestrutura de **fatos relacionais** — quem conhece/
trabalhou/indicou quem, com contexto, validade, evidência e confiança — que humanos usam pela
frente (app) e agentes de IA consultam por trás (API). A rede é o ativo; a recompensa acelera, não
é o produto; o Orbitrum **registra**, não executa nem garante.

**Onde chegamos (real, não papel):** o motor de fatos roda e persiste; o loop da tese fecha numa
tela (necessidade → match com motivo → perfil "por que apareceu" → conversa → **execução real**
com barra 0–100%, mapa/caminhozinho, presença → validação → a rede aprende); as decisões difíceis
viraram CÓDIGO (fato não se apaga, validar não paga, cliente não herda competência, §35, crédito ≠
reward ≠ BRL, não custodial, localização autorizada/temporária). O design elite cobre as telas
principais sem quebrar o que existia. É a 1ª vez que a tese é navegável de ponta a ponta.

**As camadas que emergiram (todas fiéis à tese, nenhuma inventada):**
1. **Relacional** — o ativo (fatos + Trust Graph + explicação).
2. **Execução** — acompanhar o ato real (barra 0–100%, mapa, presença) → dá lastro ao fato.
3. **Continuidade** — Orbitrum conecta; o ecossistema executa (deep-links, não reconstrói Uber/etc.).
4. **Econômica** — grátis pra crescer; assinatura do pro monetiza; saque por resultado via PSP;
   sem paywall no que gera conhecimento. Congelada no papel até a spec jurídica + parecer.
5. **Agentes** — Orbitrum consultável por IAs externas; worker mantém os fatos vivos.

**Conclusão honesta:** a tecnologia não é mais o gargalo — o motor, o loop e as travas existem e
rodam. O gargalo é **densidade e adesão** (onde redes morrem) e o **enquadramento jurídico** da
economia (a fazer com advogado/contador antes de qualquer código de saque). O custo baixo
(~R$2k/mês, break-even ~100–150 pagantes) dá runway longo pra construir densidade numa cidade/
categoria. A ordem continua: **útil para uma pessoa numa cidade antes de indispensável para um
agente no mundo.** O próximo passo NÃO é mais código de economia nem IA — é acabamento elite +
camada de execução completa (bilateral/ring/relatório) + densidade; a economia e os agentes entram
depois, na ordem certa.

### Fase E — Deploy Vercel (backend + frontend no mesmo deploy)

**Contexto:** o repo OrbitrumProConnect no Vercel já rodava antes (outra base de código). Empurramos
o orbitrumexpopro pra lá (fast-forward 66aa64d). O primeiro build falhou: `cd client: No such file
or directory` — o root package.json tinha `"workspaces": ["frontend","backend"]` (Expo morto da época)
que fazia o `npm install` reorganizar o filesystem.

**Reavaliação Vercel 2026:** em 2026, Vercel hospeda backend Node/Express (zero-config, functions).
O motor da tese é stateless + DB-backed → compatível com serverless. Não precisa Railway nem host
externo. Direção: **Vercel (frontend + API function) + Supabase (dados)** — padrão dos outros apps.

**O que foi feito (commits 13c8dc0, 501c14c):**

1. **`api/index.ts`** criado — entry serverless que importa `app` e `ready` do backend/index.ts e
   expõe como handler. Na Vercel, o Express inteiro roda como uma function.
2. **`backend/index.ts`** guardado:
   - `export const app` + `export const ready` (IIFE que registra rotas e retorna app)
   - `const IS_VERCEL = !!process.env.VERCEL`
   - Guards: WebSocket/cron/supabaseSync/notifications → `if (!IS_VERCEL)` (serverless não segura processo)
   - Vite/serveStatic → `if (!IS_VERCEL)` (Vercel serve o frontend)
   - `server.listen()` + healthMonitoring → `if (!IS_VERCEL)` (function exporta handler, não dá listen)
   - `return app;` no final da IIFE
3. **`package.json` raiz** — removido `"workspaces"` morto; adicionadas TODAS as deps do backend como
   deps raiz (express, drizzle-orm, postgres, express-session, node-cron, etc.) pra function resolver.
   Removido package-lock.json antigo (tinha refs de workspaces).
4. **`vercel.json`** — `installCommand: npm install --legacy-peer-deps` (deps raiz = backend);
   `buildCommand: cd client && npm install --legacy-peer-deps && npm run build:no-check` (deps + build
   do frontend); `outputDirectory: client/dist`; `functions: api/index.ts` com `includeFiles:
   backend/**,shared/**`; `rewrites: /api/* → api/index.ts, /* → index.html`.
5. **`tsconfig.json` raiz** — removido `expo/tsconfig.base` morto; paths `@shared/* → backend/shared/*`
   (o schema REAL do Drizzle, não o client-safe de shared/).

**Dificuldades / aprendizados:**
- `shared/schema.ts` (raiz) ≠ `backend/shared/schema.ts`: raiz é client-safe (mocks/types), backend
  é o schema real (pgTable, drizzle). O front resolve `@shared` via Vite alias → raiz; o backend
  resolve via tsconfig paths → `backend/shared/`. Não confundir.
- `frontend/` = Expo morto da época (nunca usado no app atual). `server/` idem. Só `client/` + `backend/` + `shared/` importam.
- `canvas` (dep nativa de report-generator.ts) é importada com `await import()` (lazy) → não quebra cold start.
- O root `.npmrc` tem `legacy-peer-deps = true` mas a Vercel pode não respeitar no contexto do client — por isso `--legacy-peer-deps` explícito no comando.
